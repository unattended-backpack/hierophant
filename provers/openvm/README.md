# Vendored OpenVM assets

Same contract as the sibling `sp1/` and `risc0/` directories: only `.sha256`
sidecars are committed here; the bytes live on the CDN at
`${VENDOR_BASE_URL}/openvm/...` and are downloaded then checksum-verified by
`container/vendor.sh` at image-build time.

## `git/<tag>/`

Bare-mirror tarballs of the two OpenVM git dependencies
(`openvm-git-mirror.tar.gz`, `stark-backend-git-mirror.tar.gz`), taken at the
workspace's pinned tag. The Dockerfiles rewrite the canonical repository URLs
to these mirrors (git `insteadOf` + cargo `net.git-fetch-with-cli`), so builds
never fetch unvendored OpenVM source; cargo's lockfile commit-SHA check then
re-verifies the mirror served exactly the pinned commits. Regenerate with
`git clone --mirror` of each repository, confirm `git rev-parse <tag>^{commit}`
matches the SHA recorded in `Cargo.lock`, tar, and upload.

## `halo2/<line>/openvm-agg-keys.tar.gz`

The `halo2/` axis is keyed by the OpenVM minor line (for example `v2.0`)
rather than the SDK patch tag. Upstream regenerates the halo2 circuits and
their keys per minor release and holds them stable across patch releases,
so a patch bump of the SDK reuses the same key material without a fresh
multi-gigabyte upload. `petros` pins the same artifacts under its
`src/openvm/halo2/<line>/` and verifies them by regeneration.

The deterministic aggregation keys (`internal_recursive.pk` + `.vk` +
`root.pk`, the root key required whenever `halo2.pk` is seeded for EVM
proving) staged into both images' `~/.openvm/` when
`OPENVM_AGG_KEYS_VERSION` is set in `.env.maintainer`. Generated by `petros`'s
`src/scripts/generate-openvm-agg-keys.sh`; verify by regeneration on
independent hardware (the script prints the per-file hashes to compare).

## `halo2/<line>/openvm-halo2-pk.tar.gz`

The OpenVM EVM (halo2) proving key, mirrored from upstream's public artifact
bucket and shipped gzip-compressed: the key's structured regions compress
~30% (9.4 GB raw → ~6.5 GB on the wire), unlike the KZG params below which
are incompressible curve points. Two committed sidecars serve two purposes:
`openvm-halo2-pk.tar.gz.sha256` is the transport pin `vendor.sh` checks at
image build, and `halo2.pk.sha256` pins the *contained* key so the
trusted-setup reproduce-and-compare (petros's `docs/OPENVM_TRUSTED_SETUP.md`)
and out-of-band provisioning can verify content identity directly.

It is baked into the `contemplant` image's `~/.openvm/` when
`OPENVM_EVM_ASSETS_VERSION` is set in `.env.maintainer`. This is the deployment
default, so rental-fleet images (Vast.ai and similar, where volume mounting
is unreliable) are fully self-contained. Lean images (variable empty) can
still serve EVM via a volume mount over `/home/contemplant/.openvm`.

## `kzg/<contribution>/`

Checksum sidecars for the `kzg_bn254_{10..24}.srs` KZG params this repository's
EVM-asset bake fetches (raw files; the bytes live once on the CDN, shared
with `petros`'s verification copies under its `src/openvm/kzg/`). Each
consumer commits its own pins.
